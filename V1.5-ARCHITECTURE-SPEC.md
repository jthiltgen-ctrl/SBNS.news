# SBNS v1.5 Production Architecture Specification

Version: v1.5 architecture specification

Status: Design contract only. This document does not implement or authorize infrastructure.

## 1. Purpose

SBNS v1.5 is the transition from the fixture-backed v1.4 editorial prototype to an authenticated, durable, live-assisted editorial system.

The target workflow is:

```text
editor / visitor / monitor / discovery
                    ↓
              persistent intake
                    ↓
               live research
                    ↓
            evidence-aware analysis
                    ↓
              human editorial review
                    ↓
             human approval gate
                    ↓
           controlled repository PR
                    ↓
              publication/deploy
                    ↓
          monitoring/correction loop
```

The governing editorial invariant remains:

> The system exists to make careful editorial work faster. It must not make careless editorial work easier.

## 2. v1.4 baseline

The completed v1.4 system established five incremental phases:

- **Phase A — Intake analysis contract:** machine-readable intake-analysis schemas, golden fixtures, and deterministic validation.
- **Phase B — Read-only administrator prototype:** fixture-backed intake recommendations displayed without mutation.
- **Phase C — Editable human editorial review:** local editing and ephemeral human decisions kept separate from analyzer output.
- **Phase D — Human-gated publication:** a browser-generated publication package and deterministic repository-local preparation guarded by explicit approval.
- **Phase E — Monitoring and corrections review:** fixture-backed no-action, update, correction, and follow-up review semantics without story mutation.

At the beginning of v1.5, the authorized workers.dev staging deployment contains:

- 11 published stories;
- 3 intake fixtures;
- 3 monitoring fixtures;
- 13 intake negative tests;
- 21 monitoring scenarios;
- 18 publication scenarios;
- no live analyzer;
- no persistence;
- no authentication;
- no browser mutation API.

These deterministic fixtures and tests remain regression assets while live capabilities are introduced.

## 3. v1.5 architectural principles

1. Human decisions remain authoritative.
2. AI never publishes.
3. Public submissions never create public stories directly.
4. Analyzer output and human decisions remain separate data.
5. Published story JSON remains repository-managed.
6. D1 stores editorial state; it is not the public content source of truth.
7. Browser clients never receive GitHub credentials.
8. Secrets remain server-side.
9. Publication mutations are auditable.
10. Corrections preserve history.
11. Every asynchronous job is idempotent and retriable.
12. Evidence remains inspectable by the editor.

## System architecture

## 4. Logical components

The architecture consists of the following conceptually separate components, even if some initially execute in the same Cloudflare Worker:

- **Public Website:** static-first reader experience backed by the repository-generated feed.
- **Public Submission Form:** abuse-resistant URL intake for visitors.
- **Administrator Editorial Desk:** authenticated, mobile-first queue, analysis, drafting, decision, publication, and monitoring interface.
- **SBNS Worker API:** public and privileged HTTP boundary, validation layer, and job orchestration entry point.
- **D1 Editorial Database:** durable internal workflow, revision, decision, and audit state.
- **Analysis Queue:** asynchronous intake and source-enrichment jobs.
- **Analysis Worker/Consumer:** source retrieval, analysis orchestration, validation, and persistence.
- **AI Provider Adapter:** vendor-neutral editorial-analysis interface.
- **AI Gateway:** model observability, routing, cost controls, and safe caching policy.
- **GitHub Publication Adapter:** server-side GitHub App integration for deterministic branches, commits, and draft PRs.
- **Repository/Public Story Layer:** `content/stories/*.json` plus deterministic `public/stories.json` generation.
- **Monitoring Queue:** asynchronous checks for later developments.
- **Monitoring Worker:** evidence retrieval and validated monitoring recommendations without direct story mutation.

Conceptual separation is required so authentication, authorization, persistence, research, inference, publication, and public delivery can evolve independently.

## 5. Public website

The public website remains static-first and publicly accessible. Published story truth remains in:

```text
content/stories/*.json
```

The public feed remains deterministically generated as:

```text
public/stories.json
```

D1 must not replace this repository-managed public content model. The homepage may eventually add **Submit a story**, but only after durable intake exists and the public submission protections in this specification are implemented.

## 6. Administrator authentication

SBNS selects **Cloudflare Access** as the primary authentication layer for:

```text
/admin/*
/api/admin/*
```

Public routes remain outside the Access boundary. SBNS must not invent a separate username/password system when Access can provide the identity-aware proxy. Cloudflare supports path-specific protection for self-hosted applications; see [Cloudflare Access HTTP applications](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/).

The Worker must still validate the expected authenticated identity and context for privileged API operations. Hiding UI controls in browser JavaScript is not authorization.

Before implementation changes DNS or production routing, the implementation milestone must verify the exact Access hostname, application, and path configuration. This specification alone authorizes no production DNS, domain, route, or nameserver change.

## 7. Authorization

The initial application role is:

- `editor`

The model remains compatible with later roles:

- `editor`
- `reviewer`
- `administrator`

Role complexity should not be introduced until more than one human role is operationally necessary. Server-side authorization determines whether privileged operations are permitted. The authenticated actor and authorized action must be recorded for consequential mutations.

## Persistence

## 8. D1 decision

SBNS selects **Cloudflare D1** for durable internal editorial state. D1 is justified in v1.5 by the need for:

- a durable intake queue;
- relational source and claim relationships;
- human decisions tied to exact draft revisions;
- revision history;
- monitoring events;
- duplicate relationships;
- publication attempts;
- an append-oriented audit trail.

Schema evolution must use checked-in SQL migrations under:

```text
migrations/
```

Cloudflare supports versioned migration files tracked with the project; see [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/).

No D1 database, binding, or migration is created by this specification.

## 9. Source-of-truth boundaries

The boundaries are explicit:

```text
D1                  = editorial workflow state
Git repository      = published story source of truth
public/stories.json = deterministic generated public feed
```

A D1 record marked approved is not proof that repository publication, merge, deployment, or verification occurred.

The system keeps these timestamps distinct:

- `submitted_at`
- `analyzed_at`
- `reviewed_at`
- `approved_at`
- `repository_prepared_at`
- `merged_at`
- `deployed_at`
- `published_at`

## 11. Private visitor contact information

Visitor contact details must not be mixed into analysis, editorial draft, publication package, or public story payloads. If contact is collected later, it should use a separate minimal-retention table such as `submission_contacts` with narrowly scoped access and deletion policy.

Contact information must never appear in public story JSON.

## Intake queue

## 12. Canonical intake lifecycle

The canonical intake lifecycle is:

```text
submitted
queued
analyzing
review_ready
editing
held
rejected
approved
publication_pending
publication_pr_open
published
failed
```

This lifecycle is distinct from analyzer recommendation. For example, this is valid:

```text
intake.status = review_ready
analysis.recommendation = hold
```

Recommendation describes machine analysis; status describes workflow position.

## 13. Queue UI

`/admin/` evolves from a one-off fixture analyzer into a persistent editorial desk. A queue card should show:

- origin;
- submitted time;
- recommendation;
- confidence;
- category;
- severity;
- status;
- factual and legal risk;
- source sufficiency;
- duplicate risk;
- last activity.

Initial filters should include:

- Needs review
- Held
- Approved
- Rejected
- Published
- Origin
- Category

Mobile remains first-class. Core queue review, editing, and decisions must work from an iPhone-sized viewport.

## Public visitor submissions

## 14. Submit-a-story flow

The public workflow is:

```text
visitor
  ↓
source URL
  ↓
“Why this matters” text
  ↓
optional contact
  ↓
Turnstile
  ↓
POST /api/submissions
  ↓
server validation
  ↓
D1 intake(origin=visitor)
  ↓
analysis queue
```

Visitor submissions never become public stories automatically.

## 15. Turnstile

Public submissions require Cloudflare Turnstile. Server-side Siteverify validation is mandatory before a submission is accepted; client completion alone is insufficient. The Turnstile secret remains server-side. See [Turnstile server-side validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

The endpoint also requires:

- rate limiting;
- maximum note length;
- strict URL validation;
- duplicate-submission detection;
- no executable uploads in initial v1.5;
- generic public failure messages;
- abuse logging that avoids unnecessary sensitive data.

## Live URL research

## 16. Server-side URL retrieval

Browser clients must never fetch arbitrary submitted URLs. The Worker or backend retrieves sources server-side with SSRF protections:

- allow HTTP and HTTPS only;
- reject URL credentials;
- reject localhost;
- reject private, link-local, loopback, multicast, and reserved network destinations;
- enforce a redirect limit;
- resolve and revalidate every redirect destination;
- enforce a response-size cap;
- enforce connection and total timeouts;
- allow only accepted content types;
- sanitize or strip HTML into a bounded representation;
- never execute source JavaScript;
- never send SBNS secrets, cookies, or privileged headers to source sites.

The initial analyzer supports ordinary HTML and document sources without browser automation. Browser Rendering may be evaluated later only after ordinary retrieval demonstrably fails for high-value sources and a separate implementation is approved.

## 17. Source preservation

Persist sufficient provenance to reproduce why an analysis was made:

- source URL;
- fetch timestamp;
- normalized extracted text or another bounded source representation;
- content hash;
- title;
- detectable publication and update metadata.

Do not retain unnecessary full copyrighted pages indefinitely. Retention should preserve evidence and reproducibility while minimizing copied content and private data.

## Asynchronous processing

## 18. Cloudflare Queues

SBNS selects Cloudflare Queues for asynchronous work. Separate logical job types are:

- `intake_analysis`
- `source_enrichment`
- `monitoring_check`
- `duplicate_analysis`

Queues allow user-facing requests to enqueue work rather than wait for an entire research pipeline, and support retries, batching, and dead-letter handling. See [Cloudflare Queues](https://developers.cloudflare.com/queues/).

## 19. Idempotency

Every queued job includes:

```text
job_id
intake_id or story_id
job_type
attempt
created_at
```

Consumers must tolerate duplicate delivery. D1 transitions must be conditional and idempotent. Reprocessing must not create duplicate analyses, drafts, monitoring events, or publication attempts. External operations should record stable operation keys and reconcile uncertain outcomes before retrying.

## AI and analysis

## 20. AI-provider abstraction

Editorial logic must not bind directly to one model vendor. The provider boundary exposes interfaces conceptually equivalent to:

```text
analyzeIntake(evidence, context)
analyzeMonitoring(evidence, baseline)
```

Returned objects must validate against the existing SBNS schemas before being persisted as valid analysis. Invalid model output results in:

```text
analysis_status = failed
```

It must never become “best effort” publication content.

## 21. AI Gateway

Model inference should pass through Cloudflare AI Gateway when the selected provider is supported. Gateway responsibilities may include:

- observability;
- provider abstraction and routing;
- request-logging controls;
- caching only where editorially safe;
- cost visibility.

Cloudflare provides a unified path for Workers AI and supported third-party model traffic; see [Workers AI unified billing and AI Gateway](https://developers.cloudflare.com/changelog/post/2026-08-07-workers-ai-unified-billing/).

This architecture does not select a permanent model. Model choice is an implementation and configuration decision.

## 22. Deterministic post-model validation

AI never determines its own validity. The pipeline is:

```text
evidence
   ↓
AI output
   ↓
JSON parse
   ↓
schema validation
   ↓
semantic invariant validation
   ↓
persist analysis
```

Existing v1.4 invariants remain binding, including:

```text
observed_condition != attributable_failure
clean_audit != no_findings
institutional_failure != proven_specific_harm_causation
later_development != original_error
```

## 23. Duplicate detection

Duplicate detection is staged.

### Deterministic comparison

Compare:

- normalized URLs;
- source domains;
- story IDs;
- linked report or audit identifiers;
- exact and near-exact titles.

### Semantic comparison

Compare:

- institution;
- event;
- underlying systemic failure;
- later development;
- published story corpus;
- active intake queue.

Duplicate detection returns risk and context to the editor. It does not automatically reject a candidate.

## Administrator API

## 24. API namespaces

Proposed privileged and public endpoints are:

```text
GET    /api/admin/intakes
POST   /api/admin/intakes
GET    /api/admin/intakes/:id
POST   /api/admin/intakes/:id/reanalyze
POST   /api/admin/intakes/:id/drafts
POST   /api/admin/intakes/:id/decisions
POST   /api/admin/intakes/:id/publication

GET    /api/admin/monitoring
GET    /api/admin/monitoring/:id
POST   /api/admin/monitoring/:id/decisions

POST   /api/submissions
```

This namespace is architectural guidance, not authorization to implement all routes at once.

## 25. API rules

APIs require:

- JSON-only request and response bodies where applicable;
- explicit body-size limits;
- server-side schema and semantic validation;
- a consistent error envelope;
- no secrets in responses;
- authenticated actor recording for admin mutations;
- idempotency keys for consequential writes;
- audit events for decisions and publication actions.

## Publication orchestration

## 26. Publication principle

Phase D's central rule remains:

```text
human approval != publication
```

Only an approved exact draft revision may enter publication orchestration. Editing after approval invalidates the decision and requires a new human review and approval.

## 27. GitHub credential architecture

SBNS selects a **GitHub App**, not a personal access token, long-lived user OAuth token, or browser-held credential.

The expected eventual minimum repository permissions are:

- **Contents: write**
- **Pull requests: write**
- **Metadata: read**

Workflow or administration permissions must not be requested unless a later implementation proves they are necessary. GitHub Apps begin with no permissions and should receive only the minimum required; see [GitHub App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app).

The GitHub App private key and installation credentials remain server-side and never enter browser JavaScript or D1.

## 28. Publication workflow

The proposed server-side workflow is:

```text
approved exact draft
        ↓
generate deterministic public story
        ↓
validate
        ↓
create unique publication branch
        ↓
create content/stories/<id>.json
        ↓
regenerate public/stories.json deterministically
        ↓
validate resulting repository state
        ↓
commit
        ↓
open draft PR
        ↓
human GitHub review/merge
        ↓
deploy authorized environment
        ↓
verify live
        ↓
mark publication complete
```

Initial v1.5 automation stops at draft PR creation. It must not auto-merge, bypass repository review, or deploy without separate authorization.

## 29. Publication failure

Publication attempt states are:

```text
queued
preparing
branch_created
files_written
pr_open
merged
deployed
verified
failed
```

The system must never report `published` solely because an API call was attempted. Failure stage and message remain inspectable, and uncertain external results must be reconciled before retry.

## Monitoring

## 30. Monitoring ingestion

Monitoring candidates may originate from:

- manual editor checks;
- scheduled monitoring;
- discovery;
- institution or source updates.

A monitoring job creates a monitoring event; it does not mutate a story. Phase E's recommendation model remains:

- `no_action`
- `update_review`
- `correction_review`
- `follow_up`

## 31. Scheduled monitoring

Stories should not all be monitored at the same frequency. Monitoring policy may consider:

- severity;
- active investigation;
- known pending reports;
- litigation;
- agency promises or deadlines;
- correction risk;
- editor-selected watch status.

Scheduled execution enqueues monitoring jobs rather than performing the full workflow synchronously.

## Corrections and history

## 32. Never silently rewrite history

Published corrections require immutable revision history preserving:

- the previous published version;
- the corrected version;
- the correction note;
- supporting evidence;
- the deciding editor;
- the decision and publication timestamps.

Later context that does not make the original reporting wrong is an update or follow-up, not a correction.

## 33. Future public correction presentation

A separately approved public-schema extension may eventually add fields conceptually like:

```text
updated_at
correction_note
correction_history
```

This architecture-specification PR does not modify the current public story schema.

## Security and privacy

## 34. Trust boundaries

The following are untrusted:

- visitor input;
- submitted URLs;
- fetched source content;
- AI output.

The following become trusted only after the stated validation and authorization:

- authenticated editor action;
- schema-valid and semantically valid analysis;
- an exact approved draft revision;
- verified repository state.

Authentication alone does not make external evidence or model output true.

## 35. Secrets

The following remain server-side:

- AI credentials;
- Turnstile secret;
- GitHub App private key and installation credentials;
- any future monitoring API credentials.

Secrets must never be:

- embedded in static JavaScript;
- stored in D1;
- returned from APIs;
- committed to the repository.

## 36. Audit trail

Append-oriented audit events record:

- intake creation;
- analysis completion or failure;
- editor edits and draft revisions;
- hold, reject, and approve decisions;
- publication requests;
- GitHub branch and PR creation;
- publication failures;
- deployment and verification;
- monitoring decisions;
- correction decisions.

Normal application behavior must not rewrite or delete audit events.

## Observability

## 37. Operational visibility

Track:

- intake volume;
- analysis duration;
- analysis failure rate;
- queue backlog;
- source-fetch failures;
- AI validation failures;
- recommendation distribution;
- human override rate;
- publication failure rate;
- monitoring actionable rate.

Analytics must not receive source text, visitor contact details, or private editorial text unless explicitly necessary and separately approved.

## Rollout

## 38. v1.5 implementation sequence

### Phase 1 — Persistence foundation

- D1 binding;
- checked-in migrations;
- persistent intake, analysis, draft, decision, and audit records;
- fixture import only where needed for development.

No live AI is introduced in this phase.

### Phase 2 — Authentication and persistent admin queue

- Cloudflare Access;
- authenticated `/api/admin/*`;
- persistent queue UI;
- saved edits and decisions.

### Phase 3 — Live editor URL intake

- server-side URL retrieval;
- source normalization;
- analysis queue;
- AI adapter;
- schema and semantic validation;
- editor-submitted URLs only.

### Phase 4 — Visitor submissions

- public **Submit a story** flow;
- Turnstile;
- `origin=visitor`;
- rate limiting and abuse protections;
- the same proven downstream queue.

### Phase 5 — Controlled publication orchestration

- GitHub App;
- deterministic repository mutation;
- draft PR creation;
- required human GitHub review and merge.

### Phase 6 — Live monitoring ingestion

- queue-backed monitoring;
- scheduled and manual checks;
- Phase E review interface backed by durable records.

### Phase 7 — Corrections and update publication

- immutable revision-history model;
- correction and update repository workflow;
- separately approved public correction presentation.

## 39. Why this order

- Persistence precedes live analysis so results are not disposable.
- Authentication precedes privileged mutation so editorial state is protected.
- Editor-only live intake precedes visitor submissions to reduce the initial abuse surface.
- Visitor submissions reuse a proven internal intake and analysis path.
- Publication automation follows durable approval and audit state.
- Monitoring reuses the established retrieval and analysis machinery.
- Correction mutation is last because it changes historical public content and therefore requires the strongest revision and audit guarantees.

## 40. Infrastructure change discipline

Every implementation phase must explicitly enumerate each proposed new:

- D1 database;
- Queue;
- Access application or policy;
- secret;
- GitHub App permission;
- Worker binding;
- cron trigger;
- route or domain.

Nothing is implicitly authorized by this architecture document. Production DNS, nameserver, and domain changes remain separately approved work. Legacy GreenGeeks files remain untouched unless separately authorized.

## 41. Migration strategy

v1.5 must preserve the functioning v1.4 staging system during incremental implementation. Prefer additive migration:

```text
fixture-backed UI
        ↓
persistent equivalent
        ↓
live inputs
```

Fixture modes should not be removed immediately. Deterministic fixtures remain available as regression and test data while live paths are introduced.

## 42. Acceptance criteria for v1.5 architecture

This specification explicitly answers:

- **What authenticates editors?** Cloudflare Access protecting `/admin/*` and `/api/admin/*`.
- **What authorizes privileged actions?** Worker-side identity/context validation and server-side role checks.
- **Where does persistent workflow state live?** Cloudflare D1 with checked-in migrations.
- **What remains repository-managed?** Published `content/stories/*.json` and generated `public/stories.json`.
- **How do public submissions enter safely?** Turnstile, server validation, rate limiting, duplicate detection, abuse controls, and queued intake.
- **How are arbitrary URLs fetched safely?** Server-side retrieval with SSRF, redirect, size, timeout, and content-type controls.
- **How does asynchronous work run?** Idempotent Cloudflare Queue jobs and retriable consumers.
- **How is AI output validated?** JSON parsing, schema validation, and deterministic semantic invariants before persistence.
- **How are duplicate candidates handled?** Deterministic and semantic comparison returning editorial risk/context rather than automatic rejection.
- **How is an approved story turned into a repository PR?** A server-side GitHub App creates a deterministic branch, story/feed changes, commit, and draft PR after exact-draft approval.
- **What GitHub permissions are required?** Initially Contents write, Pull requests write, and Metadata read.
- **How are monitoring events created?** Manual, scheduled, discovery, or source-update jobs create durable events without mutation.
- **How are corrections distinguished from updates?** Corrections mean prior reporting was wrong; updates and follow-ups add later context while preserving an accurate original.
- **How is audit history retained?** Append-oriented audit events plus immutable draft, decision, publication, and correction revisions.
- **What sequence minimizes risk?** Persistence, authentication, editor-only live intake, visitor intake, controlled publication, monitoring, then correction publication.
